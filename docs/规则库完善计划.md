# ArchiKen 规则库完善计划

> 版本：v1 · 2026-10-15
> 目标：把内置规则库从 80 条扩充到行业可用水平（150+ 条），并建立可持续的规则迭代机制。

---

## 一、合规边界（先讲清楚）

| 做法 | 是否可行 | 说明 |
|---|---|---|
| 反编译 Solibri 二进制 / 解包规则库文件 | ❌ 禁止 | 违反项目合规边界，有法律风险 |
| 破解、提取 Solibri 规则参数数据 | ❌ 禁止 | 同上 |
| 阅读 Solibri **官方公开帮助文档**（规则编号/名称/用途说明） | ✅ 允许 | 公开资料，作为功能对标清单 |
| 依据 **GB 规范原文**自行编写规则 | ✅ 允许 | 规则的最终依据本来就该是国标 |
| 参考 buildingSMART IFC/IDS 公开标准 | ✅ 允许 | 项目既定路线 |
| 用**公开 IFC 样本**做验证语料 | ✅ 允许 | 解决"手头没有真实模型" |

原则：**对标 Solibri 的功能覆盖面，不复制其实现与数据**；每条规则的权威出处是 GB 规范条文。

## 二、素材来源

1. **Solibri 官方公开规则文档**（help.solibri.com）：规则编号、名称、适用构件、检查意图——作为"规则缺口对照表"，逐条标注：已覆盖 / 可表达 / 需引擎扩展 / 不适用
2. **GB 规范原文**（规则的唯一权威依据）：
   - GB 55019-2021 无障碍 · GB 50352-2019 民用建筑 · GB 50096-2011 住宅
   - GB 50016-2014(2018版) 防火 · GB 50084-2017 喷淋 · GB 50010/50011 结构
   - GB 50242/50243/50303 机电安装 · JGJ 100-2015 车库
3. **公开 IFC 验证语料**（替代真实模型）：
   - buildingSMART 官方 IFC 示例文件（IFC2x3/IFC4 各版本）
   - IfcOpenShell 仓库示例模型
   - GitHub 公开 BIM 样本（住宅/办公楼 IFC）
   - 现有 corpus/ 冒烟模型做回归基准
4. **buildingSMART IDS 标准**：规则表达式的国际对标格式

## 三、规则库分层结构

```
内置模板（kernel/app/rules/templates/）
├── common.py            通用层（12 条）：碰撞/质量/合规基础
└── compliance/          合规层（68 条，按域分包，挂 GB 出处）
    ├── accessibility.py 无障碍 14      ├── fire.py        消防 5
    ├── headroom.py      净高 13        ├── evacuation.py  疏散 10
    ├── mep.py           机电 10        ├── structure.py   结构 8
    └── openings.py      门窗 8
```

扩充后新增层：
- **深化域**：节能（外围护完整性）、给排水专项、暖通专项、电气专项
- **质量域扩充**：命名规范、属性完整性、建模规范（对标 Solibri Model Revisions 类检查）

## 四、阶段计划

### Phase A：缺口映射与恢复（里程碑 A：对照表 + 恢复 80 条）

1. 恢复被删的规则文件（git 提交 `c8eb0d4`/`a6893f4` 都在，一条命令还原）
2. 建立 **Solibri 公开规则 → ArchiKen 缺口对照表**（`docs/solibri规则对照表.md`）：
   - 逐条登记 Solibri 公开规则编号/名称
   - 标注三档：✅ 已覆盖 / 🔧 现有引擎可表达（待写）/ 🚧 需引擎扩展
3. 优先补 🔧 档规则（纯配置，预计 40+ 条）

### Phase B：引擎能力扩展（里程碑 B：4 个新检查能力）

按缺口对照表中出现频率排序实现：

| 能力 | 用途 | 改动范围 |
|---|---|---|
| count 计数检查 | 每层安全出口 ≥2、防火分区数量 | checks.py + dsl.py + evaluator.py |
| any_of 条件组（OR） | "卫生间或浴室"、"剪力墙或结构墙" | selector.py + dsl.py |
| 枚举值校验（in 已支持，补模板用法） | FireRating ∈ {甲级,乙级,丙级} | 仅模板，引擎已支持 |
| 空间包含（containment） | 消火栓必须在走道、设备必须在机房 | checks.py 新增 |

每实现一项，回填对照表中对应 🚧 规则。

### Phase C：验证语料与试跑（里程碑 C：首轮命中报告）

1. 下载公开 IFC 样本 3~5 个（buildingSMART / GitHub），登记到 `corpus/manifest`
2. 全量规则试跑，输出命中清单
3. 逐条人工标注：**真命中 / 误报 / 漏报**，记录到 `docs/规则验证记录.md`
4. 按结果调阈值与选择器（预期首轮误报集中在：相交类、命名匹配类）

### Phase D：质量闭环与沉淀（里程碑 D：可发布的规则库 v1.0）

1. 规则分级固化：error 级规则必须有明确 GB 条文 + 验证通过
2. 规则集 JSON 导出/导入（团队分享）
3. 报告引用规范条文（reference 字段已就位，接进报告模板）
4. 形成"规则编写规范"文档：命名、severity 定级标准、阈值来源标注要求

## 五、验收标准

- 数量：内置模板 ≥ 150 条，其中 error 级 ≥ 40 条且全部挂 GB 条文
- 质量：公开语料上 error 级规则误报率 < 30%（首轮人工标注）
- 覆盖：对照表中 Solibri 常用规则（其官方文档标注的高频项）覆盖率 ≥ 70%
- 工程：DSL 解析全通过、ID 无重复、8+ 预设可用、readme/调试日志同步

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| 命名匹配类规则误报高（靠 Name contains） | Phase C 验证后加"匹配模式"说明 + 允许用户自定义关键词 |
| 公开 IFC 样本与真实项目差异大 | 语料登记来源与特征；用户后续拿到真模型后复跑对比 |
| GB 条文理解偏差 | 每条规则的 reference 写到条/款级，便于复查；拿不准的降为 warning/info |
| 引擎扩展引入回归 | 每个新检查能力配 corpus 冒烟用例，跑通再合入 |
