# ArchiKen 逆向开发技术路线与分阶段开发计划

> 对标对象：Solibri（Solibri Office / Site / Anywhere / WebChecker / Autorun）
> 版本：V0.2（草案）
> 编制日期：2026-10-13
> 语言：中文

---

## 0. 摘要

ArchiKen 的目标是构建一款与 Solibri 同级、在某些指标上超越的 BIM 模型质量检查与合规审查产品。本方案给出两部分内容：

1. **技术路线**：核心功能逆向拆解方案、技术栈选型、微服务+桌面端混合架构设计、关键技术难点预研方案。
2. **分阶段开发计划**：五个阶段（逆向分析 → 核心验证 → 功能对标 → 兼容性/性能 → 测试发布），每阶段明确交付物、时间节点（周）、验收标准。

**核心结论（三条）**

- 技术地基采用 **IfcOpenShell 原生服务**（Python + C++/OpenCASCADE），桌面端采用 **Electron + React/TS**，两者以本机进程 + HTTP/gRPC 通信，形成"微服务 + 桌面端"混合架构。
- 全部对标工作基于 **黑盒功能分析** 与 **公开国际标准**（IFC2X3/IFC4/IFC4X1/IFC4X3、IDS、BCF、Excel 报表格式），**不做二进制反编译、不破解授权、不复刻其私有 .smc 文件格式**。
- 采用"**黄金基准比对**"方法学：以 Solibri 在同一批测试模型上的输出（通过项/冲突项/坐标/报表）作为基准，逐模块量化 recall / precision 与性能比值，用数字驱动验收。

**部署定位**：**桌面单机版为主形态**，云端企业集群版为**批量自动化与结果分发载体**（Autorun / WebChecker），不做浏览器 SaaS 主形态、不在云端承载交互式 3D 渲染。

|---|---|---|
| 工作目录 `.../aitools/AchiAudit` | 空目录，无任何文件（已实际核实） | 全新项目，无历史代码包袱，可自由定架构 |
| 同级目录 `.../aitools/Architect` | 存在一个成型项目（Node/TS + Vite + React + Koa 后端） | 可作为工程脚手架、目录规范、鉴权/打包流程的参照模板 |
| 项目记忆 | 无 AchiAudit 相关历史记录 | 无既定约定约束 |
| 团队既有能力 | Node.js / TypeScript / Koa / Express / MySQL / Redis / React / Redux / Vite | UI 层与业务层零学习成本；**几何/BIM 内核能力为空白**，必须依赖成熟开源内核 |

### 1.2 能力缺口（决定选型的关键事实）

1. **无 IFC 语义解析经验** → 不自研 IFC 解析器，直接采用 IfcOpenShell。
2. **无几何算法团队** → 碰撞检测采用"成熟算法库 + 自研调度层"，而非从零写 CSG/BVH。
3. **无 BIM 行业语料** → 需在第 1 阶段建立回归语料库（buildingSMART 官方样例 + 各导出方样本），否则无法量化"对标"。
4. **对标口径问题** → Solibri 的"通过/失败"判定在参数边界处存在自定义语义，必须通过探针模型（probe models）实测逼近，不能凭文档臆测。

## 2. 技术路线

### 2.1 核心功能逆向拆解方案

#### 2.1.1 Solibri 功能矩阵（对标清单）

以下为经公开资料确认的 Solibri 核心模块，作为 ArchiKen 的功能对标基线：

| 编号 | 模块 | Solibri 行为特征 | 对标优先级 |
|---|---|---|---|
| M1 | 模型加载与融合（Federation） | 多 IFC 文件合并、按文件/创建软件/命名自动映射**专业分类（Discipline）**、模型树与空间层级 | P0 |
| M2 | 模型解析与几何处理 | 参数化几何转显式几何、布尔运算、扫掠体、单位换算与**地理参考**处理 | P0 |
| M3 | 规则引擎与规则集（Ruleset） | 内置 **50+ 规则模板**，参数化配置（组件 + 属性/分类筛选 + 算子 + 取值），规则集可保存/复用 | P0 |
| M4 | 碰撞/干涉检测（Clash Detection） | **冲突矩阵（Clash Matrix）** 按专业两两对检；硬碰撞、间隙（软碰撞）、净空检查；忽略规则 | P0 |
| M5 | 合规性检查（Compliance） | 门净宽/无障碍、空间净高、消防间距、结构/建筑一致性等 | P1 |
| M6 | 信息提取 ITO / QTO | 属性聚合、数量统计、**内嵌 JavaScript 脚本编辑器**、Excel 报表导出 | P1 |
| M7 | IDS 校验 | 基于 buildingSMART IDS（XML）校验信息交付要求；Premium 版含完整 IDS 编辑器（导入/导出/报告） | P0 |
| M8 | 结果与沟通（Communication） | 问题项（Issue）管理、责任人指派、严重度分级、**缩放快照截图**、BCF 导出 | P0 |
| M9 | 报告生成 | PDF / Excel 检查报告，含问题清单、截图、汇总统计 | P0 |
| M10 | 视图系统 | 3D 视图、剖切/剖面、2D 图纸视图、标记与演示视图 | P2 |
| M11 | 自动化（Autorun / WebChecker） | 批量自动运行完整检查流程、无人值守、结果分发 | P1 |

> 优先级口径：**P0 = 进入第 2 阶段最小原型；P1 = 第 3 阶段重点模块；P2 = 第 3 阶段尾期/第 4 阶段。**

#### 2.1.2 逆向分析路径（每个模块统一走五步法）

对 M1–M11 逐一执行：

**步骤 A｜界面穷举与功能清点**
- 遍历菜单 / 工具栏 / 右键菜单 / 设置面板 / 参数对话框，截图归档。
- 产出：UI 元素清单 + 与功能矩阵的映射表（哪些 UI 对应哪个规则、哪个参数）。

**步骤 B｜数据流闭环追踪**
- 观测一次完整操作链：导入 IFC → 融合 → 配规则 → 检查 → 结果树 → 报告导出。
- 重点采集**产物文件**：`.smc` 工程文件、BCF（zip/XML）、Excel、PDF、日志。
- 对每个产物做结构解剖（zip 目录树、XML schema、Excel sheet 与列定义）。
- 注意边界：仅解析**自己导出/正当获得的产物**，不逆向其程序二进制。

**步骤 C｜规则语义还原（探针模型法）**
- 为每条规则构造一组"探针模型"（probe model）：在**判定边界两侧**各造一个构件（如门宽 899mm / 901mm 对 900mm 阈值）。
- 实测 Solibri 的 pass/fail 结果，反推其判定边界与容差。
- 产出：每条规则的**行为规格条目**（输入条件 → 判定 → 输出结果结构）。

**步骤 D｜性能基线采集**
- 固定硬件，跑分级语料（10MB / 100MB / 500MB / 1GB；1 万 / 10 万 / 100 万构件）。
- 记录：打开耗时、检查耗时、峰值内存、交互帧率、报告生成耗时。
- 产出：性能基线报告，作为第 4 阶段验收的对照表。

**步骤 E｜技术栈特征识别（仅静态观察）**
- 观察项：安装目录结构、第三方组件目录名（如 Qt / Electron / .NET 特征文件）、进程列表、网络请求、日志格式、更新机制、帮助文档 URL 结构。
- 产出：技术栈特征报告（用于验证我们的选型是否在同一量级）。
- **红线**：不反编译、不脱壳、不绕过授权、不抓取私有协议密钥。

#### 2.1.3 逆向分析交付物

- 《Solibri 功能矩阵与行为规格说明书》（M1–M11 全量，含每条规则模板的行为规格条目）
- 《核心模块调用链与数据流图》（含文件产物结构解剖）
- 《Solibri 技术栈特征报告》
- 《回归语料库 v1》（分级规模 × 4 大导出方 × 4 个 IFC 版本）
- 《Solibri 性能基线报告》

### 2.2 技术栈选型

选型原则：**内核用最成熟的、UI 用团队最熟的、标准用国际通用的、自研只做差异化的部分。**

| 层/模块 | 选定方案 | 备选 | 决策理由 |
|---|---|---|---|
| 桌面壳 | **Electron（最新 LTS）+ electron-builder** | Tauri | 复用团队 TS/React 能力；跨平台打包成熟；内核以本地进程接入无 ABI 障碍 |
| UI 框架 | **React 18 + TypeScript + Vite** | Vue | 与团队既有栈、既有 Architect 项目一致，零学习成本 |
| UI 状态 | **Zustand（局部）+ Redux Toolkit（全局）** | MobX | 大型模型树/结果集需要可预测状态；与既有习惯一致 |
| 3D 渲染 | **three.js** + 自研图元/实例化层 | Babylon.js | 生态最丰富；`three-mesh-bvh` 可直接支撑空间查询与拾取 |
| IFC 解析与几何内核 | **IfcOpenShell**（Python 3.11 绑定，C++/OpenCASCADE 内核） | IfcOpenShell Web(WASM) / ifc-lite(Rust) | 成熟度最高；覆盖 IFC2X3/IFC4/IFC4X1/IFC4X3；自带几何引擎与 `ifctester`(IDS) |
| 内核服务框架 | **Python + FastAPI + uvicorn（本机 127.0.0.1）** | gRPC only | 开发快、调试易；控制面 REST，大几何面走 gRPC/流式 |
| 几何缓存格式 | **预编译几何缓存**（量化 mesh + 每构件 BVH，类 Fragments 思路，自研 `.kengeo`） | 直接用 Fragments | 避免每次打开重算几何；可内嵌 BVH 加速碰撞与拾取 |
| 碰撞检测 | **自研 broad-phase**（网格哈希/AABB 扫描）+ narrow-phase（三角形 SAT/BVH；可选 `python-fcl`/`coal`） | 纯 FCL | 需要与 Solibri 一致的分类语义（硬/间隙/净空/接触面积阈值），算法库只做底层几何判定 |
| 规则引擎 | **自研 JSON/YAML 规则 DSL + 模板参数化 + Python 求值器** | Drools | 规则模型必须逐字对齐 Solibri 的"组件+属性/分类筛选+算子+取值"结构；Drools 语义不匹配且过重 |
| 规则内嵌脚本 | **受控沙箱 JS**（QuickJS 或 isolated-vm） | 无 | 对标 Solibri ITO 的 JS 编辑器，但不能让其逃逸到宿主 |
| IDS 校验 | **ifctester（IfcOpenShell）+ 自研 IDS 编辑器/报告** | 自研全量 | ifctester 官方实现，一致性最好 |
| BCF 交换 | **自研 BCF 2.1 / 3.0 读写器（XML + zip）** | 第三方库 | BCF 结构简单；需与 Solibri/BIMcollab/Revit 互通，自研可控 |
| 业务服务 | **Node.js + TypeScript + Koa** | Nest.js | 与团队既有栈一致（Architect 项目已验证） |
| 数据库 | **PostgreSQL（项目/规则/结果/权限）+ Redis（缓存/任务队列）** | MySQL | PG 的 JSONB 与索引能力更适合规则与结果这类半结构化数据 |
| 桌面本地库 | **SQLite（离线单机模式）** | — | 单机离线可用，无服务端依赖 |
| 报表 Excel | **ExcelJS（Node 侧）** | OpenXML | 支持导出与模板填充 |
| 报表 PDF | **Playwright 渲染 HTML → PDF** | wkhtmltopdf | 与前端共用一套排版代码，所见即所得 |
| 模型文件存储 | 本地文件系统（桌面）/ **S3 兼容对象存储**（企业版） | — | 双形态（单机 / 集群）共用同一适配层 |
| 打包分发 | **electron-builder**（Windows/macOS/Linux）+ 内核独立安装器 | — | 内核体积大，需独立安装/更新通道 |
| 测试 | **Vitest + Playwright（UI E2E）+ pytest（内核）** | Jest | 与 Vite/pytest 生态一致 |
| 容器化（云端） | **Docker（多阶段镜像：L2 内核镜像 / L3 业务镜像）** | — | 云端部署与本地开发同构；内核体积大但可分层缓存 |
| 编排（云端） | **Docker Compose（小规模）→ Kubernetes（企业规模化，非阻塞项）** | — | 先满足"一键起集群"，k8s 按需演进 |
| 对象存储（云端） | **S3 兼容（企业自建 MinIO / 云厂商 OSS/S3）** | — | 模型与几何缓存的云端落地；替代本地 FS |
| 鉴权（云端） | **OIDC/OAuth2 + JWT（L3 网关），内核走内部服务令牌** | — | 云端必须鉴权；内核不直接暴露公网 |
| 任务队列（云端） | **Redis Stream + worker 池（L2 无状态副本）** | — | 支撑 Autorun 批量与横向扩展 |
| 无头报表（云端） | **Playwright headless Chromium 打包进镜像** | wkhtmltopdf | 云端生成 PDF 报告，与桌面共用一套 HTML 排版 |

**一句话选型结论**：`Electron+React+three.js` 做交互，`IfcOpenShell` 做几何与语义，`Koa+PG+Redis` 做业务，规则引擎自研（这是唯一的护城河）。

#### 分层设计规范

| 层 | 职责（只做这些） | 禁止事项 | 对外契约 |
|---|---|---|---|
| **L1 数据层** | 存储与索引；模型文件、几何缓存、规则、结果、项目元数据 | 禁止含任何业务判定逻辑 | 统一 Repository 接口（TS 与 Python 各一套同签名实现） |
| **L2 核心计算层** | 纯计算：解析、几何、碰撞、规则求值、IDS、提取、报表渲染 | **禁止直连 UI**；禁止持有业务状态；每个服务可独立重跑同一输入得到同一输出（幂等） | REST/gRPC + protobuf 定义；输入输出全部走文件或内存映射，避免大几何序列化 |
| **L3 业务逻辑层** | 编排、事务、权限、状态机（检查任务生命周期）、报告与 BCF 组装 | 禁止做几何运算；禁止直接读模型二进制 | OpenAPI（REST）+ Redis Stream 事件 |
| **L4 UI 交互层** | 渲染、交互、本地视图状态；通过主进程访问 L3/L2 | 禁止在渲染进程做重计算（>16ms 的逻辑必须下沉） | 与 L3 的 REST 契约 + 事件订阅 |

#### 通信与部署规范

- **控制面**：REST（OpenAPI 契约先行），仅传元数据与小结果。
- **数据面**：gRPC + 流式（几何块、进度事件）；超大几何走**共享文件/内存映射**，不序列化。
- **事件**：Redis Stream 承载检查任务进度、模块完成通知。
- **双部署形态**：
  - *单机版（桌面）*：L2/L3 以子进程随 Electron 启动，SQLite 本地库，完全离线可用。
  - *企业版（集群）*：L2/L3 独立部署，PG + Redis + S3，支撑 Autorun 批量与 WebChecker 场景。
- **一致性要求**：同一份 IFC + 同一套规则，单机模式与集群模式输出**逐条一致**（第 4 阶段验收项）。

### 2.4 关键技术难点预研方案

#### 难点 1｜IFC 标准全版本兼容

- **难点本质**：版本间 schema 差异（IFC2X3 vs IFC4 vs IFC4X1 vs IFC4X3，IFC4X3 新增 `IfcAlignment`/`IfcBridge` 等基础设施实体）；不同导出方（Revit / ArchiCAD / Tekla / Bentley）的实体表达与属性命名习惯差异；单位制、坐标精度、地理参考（`IfcMapConversion`/`IfcSite`）处理差异。
- **攻关路径**：
  1. 建立**版本适配层**：单一解析管线 + 版本映射表（实体别名、属性别名、枚举映射），不写四套解析器。
  2. 语料库覆盖 4 版本 × 4 导出方 × 4 规模档，全部纳入 CI 回归。
  3. 单位与坐标统一在**解析入口一次性归一化**（统一到米 + 统一的工程坐标），后续所有几何与规则只面对归一化后的数据。
  4. IFC4X3 基础设施支持延后到第 4 阶段作为独立工作包（不阻塞建筑类主线）。
- **收敛判据**：语料库全量加载零崩溃、几何偏差 ≤ 1mm（相对 Solibri 同一模型）。

#### 难点 2｜大模型高性能渲染

- **难点本质**：1GB 级 IFC / 百万构件时，解析、内存、绘制三者同时成为瓶颈。
- **攻关路径**：
  1. **流式分块加载**：解析与几何化分批产出（如 100 构件/批），首批画面 1 秒内可见。
  2. **预编译几何缓存**（自研 `.kengeo`）：量化顶点 + 每构件包围盒/BVH，二次打开接近"零解析"。
  3. **渲染优化**：GPU Instancing、LOD、视锥+BVH 剔除、按需材质、合并 draw call。
  4. **并行**：几何化放到 Python 多进程；网格生成放到 Web Worker；渲染线程只做提交。
  5. **可选 WebGPU 通道**：作为第 4 阶段的性能上限探索项（非阻塞项）。
- **收敛判据**：100 万构件模型交互帧率 ≥ 20 FPS；1GB 模型首次打开 ≤ 180s、二次打开（命中缓存）≤ 20s。

#### 难点 3｜复杂规则引擎实现

- **难点本质**：Solibri 的规则不是"一个函数"，而是**组件筛选 + 属性/分类条件 + 算子 + 阈值 + 检查范围**的组合体，且规则间存在依赖与范围交集；同时要求结果可解释（命中原因链）。
- **攻关路径**：
  1. **规则模型对齐**：DSL 结构严格映射 Solibri 的规则参数面板语义（Component / Property / Classification / Operator / Value / Scope）。
  2. **求值器分层**：筛选层（用属性/空间索引做集合运算）→ 判定层（几何/数值判定）→ 结果层（生成带原因链的 Issue 对象）。
  3. **性能**：空间索引 + 构件级缓存；同批次检查增量复用中间结果。
  4. **可解释性**：每个判定输出 `{命中构件, 判定条件, 实际值, 阈值, 原因}`，直接驱动 UI 结果树与报告。
  5. **规则模板库**：第 3 阶段以 Solibri 的 50+ 模板为清单，逐条实现并做行为规格对齐测试。
- **收敛判据**：50+ 规则模板覆盖 ≥ 90%，同一探针模型集的判定结果与 Solibri 一致率 ≥ 95%。

#### 难点 4｜碰撞检测的精度与性能一致性

- **难点本质**：Solibri 的"碰撞"包含硬碰撞、间隙（软碰撞）、净空、接触面积阈值等多类语义，且带忽略规则（同专业、同系统、指定构件对）。要做到结果可比，必须还原分类语义而非只算几何相交。
- **攻关路径**：
  1. **两阶段算法**：broad-phase（网格哈希/AABB 扫描，把 O(n²) 降到可承受）→ narrow-phase（三角形 SAT + BVH，必要时 `python-fcl`/`coal`）。
  2. **语义层放在自研调度器**：几何库只回答"是否相交/最小距离"，分类（硬/间隙/净空/阈值）由调度器按规则参数判定。
  3. **冲突矩阵**：按专业两两生成任务单元，并行调度。
  4. **一致性量化**：在语料库上与 Solibri 输出做 recall / precision 比对，差异分类为"漏报/误报/坐标偏差"。
- **收敛判据**：语料库上硬碰撞 recall ≥ 90%、precision ≥ 92%；间隙/净空类 recall ≥ 85%。

#### 难点 5｜IDS 与 BCF 标准落地

- **攻关路径**：IDS 直接集成 `ifctester` 保证规范一致性，自研 IDS 编辑器与报告；BCF 自研 2.1/3.0 读写器，与 Solibri / BIMcollab / Revit 做双向互通验证。
- **收敛判据**：IDS 校验结果与 Solibri 一致率 ≥ 95%；BCF 在三大平台互导无丢失。

#### 难点 6｜桌面端与内核服务的进程模型

- **攻关路径**：主进程作为守护者（启动/健康检查/崩溃自动重启/日志归集）；内核服务绑定 `127.0.0.1` 随机端口 + 一次性令牌鉴权；离线授权（机器指纹 + 签名许可文件）；内核版本与桌面版本兼容矩阵化。云端形态下内核为**无状态副本**，进程模型退化为"副本 + 队列"，鉴权与自愈改由编排层负责。
- **收敛判据**：内核进程异常退出后 5 秒内自愈，UI 不崩溃且任务可续跑。

#### 难点 7｜对标一致性验证方法学（贯穿全程的"标尺"）

- 建立**黄金基准数据集**：同一批 IFC，在 Solibri 上跑出标准输出（通过/失败清单、冲突清单、报表）。
- 每个模块上线前跑一次**差异报告**：分类统计漏报/误报/偏差，形成差异清单并逐条收敛。
- 该方法是第 2–5 阶段所有"验收标准"的度量基础，**必须最先建立**（置于第 2 阶段开头）。

### 2.5 云端部署路线（桌面为主、云端为辅）

> 定位：云端**不是主形态**，只承载批量自动化（Autorun / WebChecker）与结果分发；交互式 3D 渲染保留在桌面端，云端无 GPU 需求（见 D7 / D8）。

1. **部署拓扑**：网关 / Ingress → **L3 业务服务**（Koa，2+ 副本，负责鉴权、租户、任务编排、结果分发）→ **Redis Stream** → **L2 内核 worker**（FastAPI，N 副本，无状态）→ **对象存储**（模型 / 几何缓存 / 报告）+ **PostgreSQL**（项目 / 规则 / 结果 / 权限）。
2. **存储适配层**：在 `kernel/app/config.py` 的 `model_roots()` 与 `geometry_cache_dir()` 之上抽象"存储后端"：`local`（桌面，现状）与 `s3`（云端），由环境变量 `ARCHIKEN_STORAGE=s3|local` 选择；云端模型以对象键定位，几何缓存按"对象键 + ETag"命名落对象存储。
3. **内核运行参数**：`--host` 默认值改为读环境变量 `ARCHIKEN_HOST`（容器内 `0.0.0.0`），端口沿用 `ARCHIKEN_PORT`；内核只在**内网**暴露，由 L3 用服务令牌调用。
4. **鉴权与租户**：L3 做 OIDC 登录 → 颁发 JWT；按租户维度隔离项目 / 模型 / 结果；内核不做用户态判定，只接受 L3 的服务令牌。
5. **任务编排（Autorun / WebChecker）**：L3 投递任务到 Redis Stream → L2 worker 拉取执行（解析 → 几何 → 碰撞 → 规则 → 报告）→ 结果与产物写回对象存储 / PG → 事件回推 L3；任务须**幂等**（同一任务重复执行结果一致），支持**断点续跑**。
6. **一致性要求（沿用 D5）**：同一份 IFC + 同一套规则，单机模式与云端模式的输出**逐条一致**；云端回归直接复用 `tools/kernel/smoke_test.py` 与语料库。
7. **可观测性与运维**：结构化日志（JSON）、保留 `/health`、指标端点按需增加；镜像按内核版本打 tag，建立"内核版本 × 桌面版本"兼容矩阵（沿用 R4）。
8. **资源与成本**：无 GPU 需求；按模型规模给 CPU / 内存配额；worker 横向扩展应对批量峰值；缓存命中率是成本关键（几何缓存必须云端共享）。
9. **CI/CD**：镜像构建 + 单机 / 云端一致性回归纳入流水线。

## 5. 验证步骤（执行期如何验收本计划）

1. **阶段门禁**：每个阶段结束时检查"交付物清单"是否齐全、"验收标准"是否用**可复跑脚本**产出数据（而非人工判定）。不达标不进入下一阶段。
2. **比对可复跑**：黄金基准比对流水线必须能在任意阶段用一条命令重跑，产出差异报告。
3. **性能可复跑**：性能基线脚本固定硬件环境，每次优化前后各跑一次，写入报告。
4. **覆盖率看板**：维护"功能矩阵覆盖率"与"规则模板覆盖率"两张看板，每完成一个模块即更新。
5. **合规自检**：每阶段复核 A1 红线（无反编译、无破解、无私有格式复刻）。
6. **工程规范自检**（遵循项目既有规则）：
   - 单模块文件 ≤ 500 行；> 800 行必须拆分（子模块同规则）；单一模块只做一件事；
   - 每次代码修改追加记录到 `debug_log_x.md`（时间 / 模块名 / 变更简述 / 备注），`debug_log_1.md` 接近 800 行时新开 `debug_log_2.md`；
   - 项目根目录维护 `readme.md`（用途 / 模块清单 / 使用说明），结构改动同步更新；
   - 代码更新自动提交 git。
7. **云端可复跑**：云端部署脚本可一条命令起集群；单机↔云端一致性回归可在流水线复跑并产出差异报告。
