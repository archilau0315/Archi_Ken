# ArchiKen 版本同步规范（单机版 ↔ 网页版）

## 核心原则：单一主干，构建目标而非分叉

**Electron 桌面端和云端 Web 端共享同一套代码库、同一套版本号、同一套发布流程。不存在两个分支，只有两个构建产物。**

---

## 1. 分支管理

```
git main（唯一主干）
  ├── kernel/        L2 Python 内核（两端共用）
  ├── server/        L3 Node 业务（两端共用）
  ├── src/           L4 React 前端（两端共用）
  │   └── services/transport.ts   传输层：Electron IPC / fetch / Nginx 反代
  ├── electron/      Electron 壳（仅桌面端打包）
  ├── deploy/        云端 Docker 编排（仅 Web 端部署）
  └── readme.md      统一文档
```

- **main** — 唯一长期分支，所有 PR 合入这里
- **release/xxx** — 发布标签分支（可选，仅用于紧急 hotfix）
- **不允许** Electron 和 Web 各自有独立分支——否则 3 个月后必然漂移

## 2. 版本号规则

```
语义化版本：主.次.修  (如 0.12.0)
```

| 场景 | 版本变更 |
|---|---|
| 内核 / 业务 / UI 新增模块（如 M12） | 次版本 +1 |
| 功能增强但不改 API 结构 | 修版本 +1 |
| Bug 修复 / 小改动 | 修版本 +1 |
| API 不兼容变更 | 主版本 +1 |

**两端版本号永远一致**。健康检查返回的 version 字段即为此值。

## 3. 构建模式切换（VITE_APP_MODE）

```powershell
# 桌面端构建（默认）
npm run build
# 或显式
$env:VITE_APP_MODE='electron'; npm run build

# 云端 Web 端构建
$env:VITE_APP_MODE='cloud'; npm run build:renderer
# 产物在 dist/，由 Nginx 托管
```

transport.ts 根据模式选择传输路径：
| 模式 | transport 分支 | 后端 |
|---|---|---|
| electron | `window.archiken.forward()` IPC | main.ts spawn python + node |
| web | `fetch(/api/*)` + vite proxy | 本机 4318/4319 |
| cloud | `fetch(/api/*)` + 同源 | Nginx 反代 → 容器 |

## 4. 同步校验（每次发布自动验证）

### 4.1 校验清单（deploy.ps1 自动执行）

| 检查项 | 验证方法 | 通过标准 |
|---|---|---|
| 内核版本一致 | `curl /health` 对比 `SERVICE_VERSION` | version 字段匹配 |
| 业务版本一致 | `curl /api/server/health` 对比 `SERVICE_VERSION` | version 字段匹配 |
| 构建 ID 一致 | 三端 health.build 字段 | 相同 commit hash + 时间戳 |
| 前端 hash 一致 | 读取 dist/index.html 中引用的 js hash | 与本次构建记录相同 |

### 4.2 版本证据输出（deploy.ps1 最后一步）

```
[5/5] 版本一致性确认...
  构建 ID:      a1b2c3d-20261015143000     ← git hash + 时间戳
  前端 hash:    8f3e2a1                    ← dist/index.html 里的产物 hash
  Git commit:   a1b2c3d                    ← git rev-parse --short HEAD
[OK] 三端版本一致，可安全切换
```

### 4.3 漂移预警（手动检查）

如果发现两端功能不一致，在 deploy/ 下执行：
```powershell
.\scripts\check-sync.ps1
# 自动比对：L2 health → L3 health → 前端 apiRequest 类型定义 → 内核路由表
# 输出任何不一致
```

## 5. 发布流程规范（每次迭代）

```
① 开发 → main 分支
② 冒烟测试（本地：npm run dev + npm run server + npm run kernel）
③ 代码评审合入
④ 打 git tag：v0.13.0
⑤ 本地构建双端产物
   ├─ electron: npm run build → electron-builder 打包 .exe
   └─ cloud:    VITE_APP_MODE=cloud npm run build → dist/
⑥ 执行 deploy.ps1 → 远端 docker compose up
⑦ 云端健康检查 + 功能冒烟
⑧ 桌面端分发（官网下载 / 自动更新）
⑨ 更新 readme.md + debug_log_x.md
```

## 6. 为什么不用分支分叉？

| 分叉风险 | 当前方案解决 |
|---|---|
| 修 Bug 要改两处漏一处 | 改一处两端同时生效 |
| 新功能先在一端"试验"导致 API 不兼容 | 先在本地 dev 验证再合入 |
| 3 个月后没人记得哪端有什么 | 版本号、health、git tag 三重锚点 |
| 合并冲突永远存在 | 无分叉即无冲突 |
